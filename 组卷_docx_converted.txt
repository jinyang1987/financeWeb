

一、先定位：组卷在系统里是哪个模块
这套 HAMS 系统的档案组织模型是**「项目→案卷→文件」三级树形结构**，核心动作全部由 OperateDataController（URL 前缀 /operate/*）+ OperateDataServiceImpl 这一个入口承接，底层是动态建表（每个档案库 LIBCODE 一套独立表）：

表名由 GlobalFinalAttr.getTableNameByParam(libcode, level) 拼成，例如 D_VOL2、D_FILE2。「组卷」的本质就是把零散文件（D_FILE）挂到某个案卷（D_VOL）下、并维护卷内顺序与档号。

二、组卷的整条业务管线
我把这条管线拆成 6 个阶段、11 个原子动作，每一格都对应到真实的 Controller 接口和 Service 方法：
①建卷/收集 → ②挂卷/拆卷 → ③排序/编号 → ④档号生成 → ⑤卷级汇总 → ⑥归档移交/装盒
阶段① 建卷（创建案卷容器）
动作：新增一个案卷（D_VOL）或项目（D_PRJ）
接口：POST /operate/addData

三、现有代码是怎么写的（含问题）
1. 入口层：Controller 薄，所有逻辑下沉到 Service
OperateDataController 仅做参数接收 + 调用 OperateDataServiceImpl，返回 RespResult。分层骨架是对的（Controller → Service → DAO），这是这套系统少有的优点。
2. Service 层：动态拼 SQL 字符串（核心实现方式，也是最大问题）
所有 D_VOL/D_FILE 操作不写具体表，而是运行时拼表名、拼 SQL：
// breakVol（打散）——反编译还原public void breakVol(Integer libcode, String volDIDs) {
    String sql = "UPDATE D_FILE" + libcode
               + " SET PID = -1 WHERE PID IN (" + volDIDs + ")";
    executeSQL(sql);   // 直接把拼接 SQL 交给 jdbcTemplate.execute
}
// mergeVol（案卷合并）public void mergeVol(Integer libcode, String volDIDs, Integer selDID) {
    Asserts.check(selDID != null && selDID != -1, "所选案卷DID不能为空/-1");
    String[] arr = volDIDs.split(",");
    List<String> src = 过滤掉 selDID 本身;
    String sql = String.format(
        "update %s set pid = %s where pid in (%s)",
        "D_FILE" + libcode, selDID, StringUtils.join(src, ","));
    executeSQL(sql);
    executeSQL("update D_VOL" + libcode + " set STATUS = 1 where did in (" + join(src) + ")");
}
3. DAO 层：MyBatis 动态表名 + ${} 裸拼
D_TABLE.xml 里全是 ${tableName}、${qxwhere}、${_parameter} 直接拼接：
<select id="search_selectForList" resultType="HashMap">
    select ${selectfields} from ${tableName}
    <if test="null != qxwhere and '' != qxwhere"> where ${qxwhere} </if>
    <if test="null != orderBy and '' != orderBy"> order by ${orderBy} </if></select>
❌ 现有实现的四大硬伤
SQL 注入面大：表名、字段、WHERE 全走 ${}，#{} 预编译被绕开（虽权限过滤部分做了，但风险真实存在）。
无事务边界：mergeVol 连续两条 UPDATE 没有显式 @Transactional，若第二条失败，卷已合并但源卷状态没更新，数据不一致。
动态表名 + EAV（D_META）混用：真实字段在 D_FILE 宽表、自定义字段又进 D_META 键值表，跨结构查询复杂、难建索引。
业务散在字符串里：档号规则、汇总规则都硬编码在 Java 拼接逻辑里，改规则要改代码。

四、最优化怎么写（我的建议 + 示例代码）
如果让我重构这套组卷能力，会做四个关键改造：
✅ 1. 用「模板方法 + 策略」把组卷管线抽成清晰骨架
把整条管线定义为一个可编排的流程，让每个动作成为独立步骤，便于复用、测试、扩展：
// 组卷管线编排器（Spring 里注入即可）@Componentpublic class VolumeAssemblyPipeline {
    private final List<VolumeStep> steps;   // 有序步骤列表

    public AssemblyResult execute(AssemblyContext ctx) {
        // 1. 建卷（容器）
        Long volId = steps.volCreator().create(ctx);
        // 2. 挂卷（把文件 PID 指向卷）
        steps.attachFiles().attach(ctx, volId);
        // 3. 排序编号
        steps.sorter().sort(ctx, volId);
        // 4. 生成并级联档号
        steps.keywordGenerator().generate(ctx, volId);
        // 5. 汇总卷级字段
        steps.aggregator().aggregate(ctx, volId);
        return AssemblyResult.of(volId);
    }
}
✅ 2. 用 @Transactional + 领域服务收敛事务边界
组卷是一个强一致操作（挂卷/合并/打散都必须整体成功或整体回滚），绝不能像现在这样裸拼多段 SQL：
@Service@Transactional(rollbackFor = Exception.class)   // 关键：整体事务public class VolumeService {
    private final VolumeRepository volRepo;
    private final FileRepository fileRepo;

    /** 合并案卷：原子性保证 */
    public void mergeVolumes(Long libId, Set<Long> srcVolIds, Long targetVolId) {
        // 1) 把源卷下的文件全部改挂到目标卷
        fileRepo.repointTo(targetVolId, srcVolIds);
        // 2) 标记源卷作废（同事务，失败一起回滚）
        volRepo.markDeprecated(srcVolIds);
        // 3) 重新汇总目标卷件数/页数
        reAggregate(targetVolId);
    }
}
✅ 3. 数据库层：保留「按库隔离」但补上约束
原方案「按档案库物理分表」在军工强隔离场景是合理的，可以保留；但要做三件事：
建表时用模板表 + 外键，或至少加 CHECK (level in (...))、对 PID 建索引；
用 MyBatis #{} 预编译，表名/字段名走白名单映射而非 ${} 直拼：
<update id="attachToVolume">
    UPDATE ${table}          <!-- 由白名单校验后的表名，非用户输入 -->
       SET PID = #{targetVolId},
           EDITOR = #{user},
           EDITTIME = #{now}
     WHERE DID IN
    <foreach collection="fileIds" item="id" open="(" separator="," close=")">
        #{id}                <!-- 预编译，防注入 -->
    </foreach></update>
用 DTO + 参数对象传参，不再把 volDIDs 拼进 SQL 字符串。
✅ 4. 把「档号规则 / 汇总规则」做成可配置（策略 + 元数据）
档号生成、卷级汇总这类业务规则应从代码中抽出来，用「规则引擎 / 配置表」驱动：
// 档号生成策略接口（各档案库可实现不同规则）public interface KeywordGenerator {
    String generate(VolumeContext ctx);   // 如 "全宗号-目录号-案卷号-件号"
}// 默认实现：按 S_DHGZ 表配置的字段顺序拼接@Componentpublic class ConfigurableKeywordGenerator implements KeywordGenerator {
    public String generate(VolumeContext ctx) {
        return ctx.getRule().getSegments().stream()
                .map(seg -> seg.resolve(ctx))   // 全宗号/案卷号/件号...
                .collect(joining("-"));
    }
}

五、结论（一句话）
组卷的业务本质是「改 D_FILE 的 PID 把它挂到 D_VOL 下 + 维护档号/汇总/盒号」，代码实现集中在 OperateDataController / OperateDataServiceImpl，用的是动态拼 SQL 的方式——功能正确但无事务、有注入风险、规则硬编码。最优写法是**「模板方法编排整条管线 + @Transactional 保证一致 + 白名单预编译 SQL + 规则策略化配置」**，既保留按库隔离的合理性，又解决原子性、安全性和可维护性。
